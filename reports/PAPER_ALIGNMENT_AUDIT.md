# VeriFlow audit: UI contracts and Dou et al. reproduction

**Historical audit (before corrections).** For the current run procedure and limitations see [BENCHMARKS.md](../BENCHMARKS.md).

Reviewed commit `b0cb725` against the attached *What is wrong with your code generated by large language models? An extensive study* (Dou et al., 2026). The attachment is byte-identical to the repository PDF. **Verdict: a paper-inspired workbench, not a validated reproduction.** Three different execution paths matter: the React app and ASP.NET API, the C# batch runner behind the published report, and the Python TIVR runner. A passing test or a matching prompt in one does not validate the others.

## UI and backend contracts

- **Single-run repair can show success without verification.** On a non-2xx response (including rejection of a locked-test hash) or a network error, `src/services/optimizationService.ts:315–359` silently switches runners. The local path re-verifies without the hash; if verification fails it synthesizes improving counts and verdicts. It can append a second round that never ran and hard-code category repair rates (`:439–554`). The UI labels these results machine-verified. Return an explicit failed/incomplete result instead; demo output should be opt-in and excluded from metrics.
- **The main start button does not send the selected mode.** `src/components/Step4Optimization.tsx:517` passes the click event directly to `onRunOptimization`. `src/App.tsx:475–506` expects a mode string. The top re-run button already uses `handleTriggerRepair`, which supplies the actual mode and sources. Test the first click as well as re-run.
- **The wire format differs from the active UI types.** `Backend/Models/RunResult.cs` emits `model`, a numeric `baselineComparator`, `baselineLabel`, and rounds with `roundIndex` and `tokenMetrics`. `src/types.ts:362–398` expects `modelId`, a nested comparator, `roundNumber` and `tokens`. Step 4 consequently falls back to its own comparator and model label (`Step4Optimization.tsx:95–96,624`), potentially calling a different model DeepSeek-R1. Contract-test a response with a non-default model and comparator.
- **Some tested contracts are not the mounted app.** `src/main.tsx` mounts `App.tsx`, which uses `src/services/*`. Generation's `/api/ai/process` and `{files}` response match `AiController`; verification and compare also have corresponding POST actions. But `src/api/endpoints.ts` expects a different `VerificationResult` on the same verify route and defines repair-session and experiment routes absent from `Backend/Controllers` and `Backend/Program.cs`. `Backend.Tests/VerificationModelsSerializationTests.cs` checks a DTO, not the live controller response. `ExperimentRunService` also constructs CLI flags such as `--feedback-regime` and `--run-id` that `tivr/run_benchmark.py` does not parse. Add a mounted-UI → actual API integration test with a deterministic provider; include success, invalid hash, and unavailable verifier cases.

## Methodology: what matches and what changes the result

| Paper requirement | Finding |
|---|---|
| **§§2–3: predefined tests; 164 HumanEval+, 399 MBPP+, 600 APPS+ (200/tier).** | Local JSONL counts match, including tier counts. But `Backend/Services/BenchmarkDatasetService.cs:164–261` and the C# batch loaders `HumanEvalPlusDataset.cs` / `MbppPlusDataset.cs` use the base `test` / assertions, not the `plus_input` suites present in those files. Passing those tests is not passing EvalPlus. The API also unconditionally marks APPS+ as stdin/stdout and only tries `solution.main()` (`BenchmarkDatasetService.cs:265–325`); e.g. `apps_plus_5341` requires a return value from `series_slices(digits, n)`. Locking a hash preserves the wrong harness just as effectively as the right one. |
| **§3.1: correct means execution succeeds and all benchmark cases pass.** | `VerificationPipeline.cs:102–127` requires pytest plus no skipped/failed/error technique for `VERIFIED`. Useful as a product quality gate, but tool availability and extra checks must not change the benchmark correctness label. Keep custom LLM-generated tests and the product verdict separate from benchmark pass rates. |
| **§4, Tables 3–4: classify the first root cause, with expert review.** | The shared taxonomy and automated diagnostics are useful approximations, not expert annotation. The reporting script also changes label meanings: e.g. `A.3` is library import error in the paper, not undefined symbols; `C.2` is hallucination, not boundary conditions. `scripts/generate_reports.py:36–51` even adds `A.4` and `B.6`. Generate labels from one definition and audit a sample against human labels before comparing distributions. |
| **§6.1 / Fig. 6: same-model repair, original task, latest failing code, taxonomy checklist and bounded feedback.** | The API `dou` branch excludes test files, constructs feedback by failure type, and renders the shared checklist (`Backend/Services/OptimizationService.cs:700–760`). Two rounds with early stopping match the intended structure. The report-producing batch runner does **not** use that prompt: `Maci.ExperimentRunner/Execution/PromptBuilder.cs:66–81` supplies a predicted category and feedback but omits the original problem and full checklist in `dou`. Improved/history/visible-evidence modes are extensions, not the paper control. |
| **§6.2 / Table 6: 120 randomly selected initially incorrect programs per model, up to two repairs.** | GPT-4 repaired 29 in round 1 and 6 more in round 2: cumulative RSR = 35/120 = 29.2%. `src/lib/paperReference.ts` correctly labels this a paper reference. But the active API summary (`OptimizationService.cs:815–833`) divides reduction in **finding count** by initial findings. A program going from two findings to one scores 50% there and 0/1 repaired programs in the paper. Step 4 puts these non-comparable values side by side. Report both under different names; use the same frozen failures for each ablation. |
| **Tables 2 and 6: measured versus reference results.** | `reports/EXPERIMENT_REPORT.md` contains 10 passes, zero initially incorrect programs, zero model rounds and zero tokens. The report run has zero `problem_rounds` in the checked-in SQLite DB. `scripts/generate_reports.py:316` substitutes canonical code when generated snapshots are absent, making the quality comparison circular. These records cannot establish generation accuracy or repair efficacy. Table 2 prints DeepSeek-R1 **69.8%** for APPS+ average and **71.2%** total; `PAPER_TARGETS` uses **71.2%** and **80.6%**, respectively. |

The full study also includes nine models, RWPB (§5), manual root-cause analysis, and matched baseline/ablation comparisons. Dataset preparation code, a reference table, or an improved-vs-Dou demo is not evidence that those experiments were run.

## Release criteria for a defensible comparison

1. Remove synthetic success paths; require traceable verifier output for every displayed round. Test the shipped app against the actual API schema, and run `dotnet test Backend.Tests/Backend.Tests.csproj` with .NET 10.
2. Use one benchmark oracle in both UI and batch runs. Include a fixture that passes base tests but fails a Plus case, and an APPS+ function-return fixture. Record dataset revisions, selected IDs, and test hashes.
3. Share one baseline prompt across runners. Fix the model/version, decoding, inputs, feedback policy, and iteration budget; change only the intended variable between ablations.
4. Refuse to publish model results without generation snapshots. Separate canonical smoke tests from live runs. Store the seeded failing cohort, round-by-round pass evidence, counts and denominators. Report N/A for no eligible failures; label smaller cohorts as pilots and the published GPT-4 value as reference only.
